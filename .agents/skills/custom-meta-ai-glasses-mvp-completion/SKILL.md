# Custom Meta AI Glasses MVP Completion

Coordinate the finite remaining MVP critical path without asking the user to supervise ordinary tests, reviews, bounded fixes, or reruns. This skill orchestrates; it never edits production code.

## Authority and operating limits

- Read `AGENTS.md`, `docs/PROJECT_MEMORY_ARCHITECTURE.md`, `docs/PROJECT_INTERACTION_FOUNDATION.md`, `docs/ROADMAP.md`, and `docs/project_constitution.md`, plus both repository statuses and the latest critical-path evidence.
- Use the minimum number of agents necessary; do not automatically fan out to the full agent team. Small, clearly bounded issues stay on `Development + QA` unless a specialist decision is material.
- Only `$custom-meta-ai-glasses-development` may edit production code, and only inside a human-authorized milestone or repair batch.
- Preserve unrelated dirty files and already accepted capabilities. Do not rebuild completed Project, Investigation, Explore, Ideas, Assistant, or HUD foundations.
- Permit at most one coherent implementation/repair batch per milestone. A genuinely second major batch is a human gate.
- Never commit, push, deploy, install, mutate configuration, or destructively change Project data without explicit authority.
- Continue automatically through successful tests, reviews, small in-batch blocker corrections, and one affected-validation rerun.
- Reuse prior validated findings rather than rerunning the same reviews; avoid broad rereads and overlapping specialist coverage.
- Do not start Research, media/video, Compare, richer glasses navigation, DAT upgrades, new persistence, generic routing/workflow infrastructure, or other post-MVP work.

## Human gates

Stop only for:

1. a material product or architecture decision;
2. destructive Project-data approval;
3. unavoidable physical hardware interaction;
4. commit, push, deployment, installation, runtime, DNS, tunnel, or configuration authority;
5. a second major implementation batch outside the current authorization.

At a gate, report the completion status and request exactly one action or decision.

## Critical path

### 1. Close Project Continuity HUD

Use existing acceptance evidence. Verify the exact protected batch, proportional QA, and Architecture Guardian verdict. If it is already committed, record the commit and continue. Otherwise stop only for required commit/push authority. Never implement unsupported suppression of Meta's platform-owned HUD.

### 2. Establish real acceptance Projects

Preserve AC Repair. Through supported canonical application behavior, create a real `Room Redesign` Project only when absent and when Project creation is authorized. It must not be a fixture. Start honestly with a warmer, modern, comfortable, functional room goal; an existing room; no selected direction; and Explore initial directions as the next action. Do not fabricate completed work or delete Projects.

### 3. Retry-safe Record Project Progress

Route product definition through Product Designer, User Tester, Trust UX Reviewer, Information Architect, Scope Guardian, Interaction Persistence Auditor, Architecture Guardian, State/Recovery, and QA Breaker; then Triage one bounded contract. Development implements only after the milestone is authorized.

The contract must preserve:

- explicit `project_id` and zero provider calls;
- preview before save;
- exactly one user-authored Activity;
- a separate Checkpoint Proposal only when canonical checkpoint fields would change;
- explicit Apply/Reject and canonical reload;
- project-scoped idempotency: equivalent same-key retries converge, conflicting reuse conflicts, concurrent requests converge, and response loss creates no duplicate Activity or Proposal;
- progress notes never directly mutate checkpoints;
- no Progress store, generic Interaction store, automatic Apply, or AI progress scoring.

Allow Development to correct only blocking findings within that batch, then rerun affected validation once.

### 4. Real-Project acceptance

Automate edge cases. Demo Scenario Designer, Product Designer, and User Tester define one short AC Repair scenario and one Room Redesign scenario. Ask the user only for unavoidable realistic hardware actions, never an artificial QA matrix. Confirm an ordinary person can leave and reopen each Project with understandable continuity and trust boundaries.

### 5. MVP hardening

Run Bug Hunter, UX Critic, User Tester, Product Designer, State/Recovery, Project Memory Auditor, API Contract Watchdog, QA Breaker, Scope Guardian, Cross-Device Designer, Physical Integration when needed, and Demo Manager. Deduplicate findings; Triage exactly one batch containing only `MVP BLOCKER` and `MVP FIX NOW` items.

Treat test-store pollution, safe deletion, visible phone-stream exit, empty/recovery states, runtime drift, and stale demo clutter as candidates—not automatic scope. Isolate test storage before any bulk cleanup. Never delete Projects until a tested canonical cascade exists and the user approves the exact regenerated deletion list.

### 6. Release candidate

After explicit deployment authority, align runtime with exact committed backend and Android HEADs, verify the permanent public backend/tunnel, build and install the exact APK, run relevant regressions, Release Sweep, Demo Manager, and one final realistic acceptance run. Return `READY FOR MVP: YES` or list only concrete release blockers. If ready, stop feature development.

## Post-MVP queue

Keep Research/references, guides, external diagrams, YouTube handoff, hosted Display video, explicit media selection for Ask/Explore, Compare, product retrieval, richer glasses navigation, DAT 0.9, improved glasses capture, and additional result families outside the critical path unless a human explicitly promotes them.
